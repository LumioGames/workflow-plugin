# rules/ —— 常驻规则的维护指南

**本目录下的 `*.md` 由 SessionStart hook 每次会话全量注入上下文**（`tools/inject-rules.mjs` 遍历目录，
排除 `README.md` 与点开头的文件，无需登记）。**本文件不注入**，它是给维护插件的人看的。

## 什么该放进常驻层

常驻成本按会话计，每加一句话，所有人每次会话都付。判据只有一条：

> **Agent 自己推不出来、或推错了就出事的**，才留在常驻层。

具体地：

- **合同陷阱**——光看 API 响应分辨不出来的事实。典型是「索引里没有 X ≠ 项目里没有 X」：
  token 没有某模块 read 权限时该类整类不出现且**不报 403**，两种情况在响应上完全一样。
- **权限与授权边界**——谁能调度、谁能写入、谁能审查、什么动作要先取得确认。
- **安全红线**——凭据、外发、公网暴露、高风险操作。
- **诚实性**——跑了才说跑了；红不得改成假绿。
- **可发现性入口**——一张极短的路由表 + 方法技能名册。方法技能不会自己冒出来，没有入口就是空洞。

## 什么必须下沉

- **操作步骤**（怎么建 worktree、模板长什么样、阈值怎么算）→ 对应技能或其 `references/`。
- **宿主适配**（各客户端能力差异）→ [`../references/host-matrix.md`](../references/host-matrix.md)。
- **维护方法**（怎么写一个子 Agent、改了要同步哪些文件）→ 本文件。
- **已有机器兜底的**——被 `plugin-lint` / `spec-lint` 强制的规则，不必再靠每次会话重读。
  例：agent frontmatter 的字段白名单由两处 lint 检查，写在这里即可。

**下沉时必须回指**：接收下沉内容的文件要在开头写明「判据在 `rules/…`，本文只展开怎么做、
不另立门」。否则 reference 会慢慢长出比主规则更严的第二套闸门——这是已经发生过一次的漂移。

**三条禁区**：不得为了压预算而删掉**权限可见性警告**、**外部输入是数据**、**方法技能导航**。

## 写法

- 规则只写「**必须 / 只能 / 不得**」。「怎么做」在各技能，「这个项目是什么」在项目 `.spec/`。
- **项目不得复制本目录任何一段**——`/workflow:lint` 的指纹检查会把「项目抄插件」报出来。
- 新增通用硬规则直接在 `system.md` 加一节；另立规则文件放进本目录即自动随会话注入。
- 改了 `rules/*.md` 必须重跑 `npm run fingerprint` 并把重生成的指纹一起提交
  （`system.md`：生成物不得手改）。

## 子 Agent 的写法

- frontmatter 只用 `name` + `description` + `tools` + `disallowedTools`；
  `role` / `goal` 等不被宿主据以调度，写了不生效。**由 `plugin-lint` 与 `spec-lint` 机器强制。**
- **能力边界必须落到 `tools` 白名单，不能只写在正文里**——只读角色就给只读工具集
  （如 `["Read", "Grep", "Glob"]`）。没有 Bash 不等于没有 `Write` / `Edit`。
- 「追求什么、用哪些技能、不做什么」写进正文。
- **改动若影响调度关系**（增删子 Agent、改流程或技能分工）**必须同步更新 `dispatch.md`**——
  漏更新 = 主 loop 调度依据失真。
