# 记 bug 的字段口径

bug 没有独立资源：`POST /work-items`，`type=bug`。以下是默认口径；字段的存在性与确切枚举以合同现查为准（见 SKILL.md 真值原则）。

## 关键字段

| 字段 | 口径 |
| --- | --- |
| `type` | 固定 `bug` |
| `status` | **不传**——后端按绑定工作流落初始态。显式传值会按该项目工作流的合法状态集校验，不在集合内直接 422；项目改过初始态名（如「待确认」）时硬写 `todo` 必失败。状态变化一律走流转端点 |
| `priority` | 用户说了才填，词表 `P0` / `P1` / `P2` / `P3`（阻断主链路 `P0`，轻微视觉/文案 `P2`）；没说就不传，让后端落默认 |
| `severity` | **用户说了才填**，词表 `blocker` / `major` / `minor`。缺省时后端不落 severity（空串＝未评估）——**不得替用户默认成 `major`**：「未评估」和「major」在缺陷分级报表里是两回事，批量记单会把严重度分布压平，QA 据此排优先级就是错的 |
| `reason` | **写明来源**，如「线上反馈记录，不启动修复」——变更记录里靠它追溯 |
| `title` | 写用户能识别的**现象**，不写内部实现猜测 |
| `description` | 至少四段：**现象**（看到什么错误）、**期望**（正确行为）、**证据**（截图/日志/复现入口/用户原话）、**记录边界**（注明「仅记录，不启动修复」） |
| `requirementId` | bug 可为空；只有用户明确说它属于某需求时才关联（传需求的 UUID，不是 `R-` 单号） |
| `ownerId` | 用户点名负责人才指派（成员名 → UUID 按合同现查成员端点；解析不到就留空并在交付时说明）；缺陷允许无主 |

## 项目自定义词表——不硬编码枚举

`role`、`customFields` 之类的词表是**项目自定义**的，不同项目不一样。**不要硬编码枚举值**，现场查：

```bash
# projectId 取自 GET /projects/current 的 project.id
curl -sS -H "Authorization: Bearer $WORKFLOW_TOKEN" \
  "$WORKFLOW_API_BASE/projects/<projectId>/bug-fields"
```

查不到或拿不准就留空，别猜一个值填进去。项目定义了必填自定义字段时，422 的 ProblemDetails 会点名缺哪个，按提示补。`customFields` 只对 `type=bug` 生效。

## 防重复建单

1. 建单前按 [search.md](search.md) 查重（`GET /search?q=<现象关键词>`，正文也会被召回；用户给了单号如 `B-00042` 就精确查）。
2. 命中疑似同一问题的 bug → 先把 `displayKey` + 标题报给用户确认，**不默默建重复单**；确认是同一个就改为在旧单上补评论/附件。
3. 网络错误或 5xx 后**先确认是否已落库**再考虑重发——这是重复建单的头号来源；「未落库」的判定以列表翻页为准（search.md 第四节）。

## 纪律

- 截图/日志里的个人信息不扩写到不必要的地方，描述只保留定位 bug 所需信息。
- 「记一下」= 只记录：不提修复方案、不建开发任务，除非用户另外要求。
- 用户没给的字段就是没给：不替他默认、不替他推断。交付时明说哪些字段留空（如「未评估严重度」「未指派负责人」），让他知道该补什么。
