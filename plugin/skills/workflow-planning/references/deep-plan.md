# 深计划：实现计划作单附件

一张需求单如果是「一个功能、一条线走到底」，就给它写一份深计划——假设执行者对代码库零上下文、品味也未必可靠：每一步碰哪些文件、写什么代码、怎么测、跑什么命令、期望什么输出，全部写出来，切成一口一口的小步。DRY、YAGNI、先失败测试、小步提交。

## 深计划还是拆单

- **深计划**：一个功能，一个执行者按步骤连续做完。写在这里。
- **拆单**：目标能拆成几块各自独立交付、独立验证的成果 → 按 [../SKILL.md](../SKILL.md) 第 3–4 节拆成多张 Requirement，各卡自带提示词；能并行的时候这是默认。
- 计划写到一半发现仍横跨多个独立子系统 → 停下退回拆单，一个子系统一份计划。

## 落点：单附件，不进仓库

- 计划是**需求单的附件**：文件名带修订号（如 `<localId>-plan-r1.md`），随 bundle 的附件清单在落单时上传；卡内「来源真值 · 原始附件」引用文件名与修订号。
- **不放进目标仓库的目录**，也不作为独立文档维护——任务真值仍是单本身，计划改了就递增修订号重新上传，旧附件保留。
- 计划里的复选框只是执行者的内部进度；完成与否以单的交付与验收项为准。

## 文件结构先于任务

定任务之前，先列出要新建 / 修改哪些文件、各自负责什么——拆分决定在这里锁定：

- 边界清楚、接口明确，一个文件一个职责。
- 能一次装进上下文的小文件比什么都干的大文件可靠；一起变的东西放一起，按职责拆而不是按技术分层拆。
- 既有代码库照既有模式；文件本来就大就别单方面重组，但正在改的文件已经臃肿时，计划里包含一次拆分是合理的。

每个任务都应产出独立成立的自包含改动。

## 任务粒度与步骤粒度

**任务**是自带验证、值得给一个新上下文写一份简报的最小单元：准备、配置、脚手架、文档并进需要它们的那个任务；只在一个任务能独立于另一个构建并验证时才拆开。每个任务以一个可独立测试的交付物结束。

**步骤**是一个动作（2–5 分钟）：

- 「写失败的测试」——一步
- 「跑它，确认失败」——一步
- 「写让测试通过的最小实现」——一步
- 「跑测试，确认通过」——一步
- 「提交」——一步

纯文档 / 配置 / 注释 / 删除类任务只保留实现、跑既有测试、提交三步，不硬造测试。

## 计划头

```markdown
# <功能名> 实现计划

> 给执行 Agent：领单后用 workflow-execute 承接，按本计划逐步做；步骤用复选框跟踪内部进度。

**目标**：<一句话说明这份计划建成什么>

**架构**：<两三句说明方案>

**技术栈**：<关键技术 / 库>

## 全局约束

<单正文或设计文档里的项目级硬要求——版本下限、依赖限制、命名与文案规则、平台要求——
一行一条，确切值逐字抄。每个任务的要求都隐含本节。>

---
```

## 任务结构

````markdown
### 任务 N：<组件名>

**文件：**
- 新建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**接口：**
- 消费：<本任务用到的、前面任务产出的东西——确切签名>
- 产出：<后面任务依赖的东西——确切函数名、参数与返回类型。执行者只看自己的任务，
  这一块是它得知相邻任务用什么名字、什么类型的唯一途径。>

- [ ] **第 1 步：写失败的测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **第 2 步：跑测试，确认失败**

运行：`pytest tests/path/test.py::test_name -v`
期望：FAIL，提示 "function not defined"

- [ ] **第 3 步：写最小实现**

```python
def function(input):
    return expected
```

- [ ] **第 4 步：跑测试，确认通过**

运行：`pytest tests/path/test.py::test_name -v`
期望：PASS

- [ ] **第 5 步：提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 不留占位

每一步都要有执行者真正需要的内容。下面这些是**计划失败**，不许出现：

- 「待定」「稍后实现」「细节之后补」
- 「补上相应的错误处理」「加校验」「处理一下边界情况」
- 「给上面的写测试」（不附测试代码）
- 「同任务 N」（把代码重复一遍——执行者可能乱序读任务）
- 只说做什么不说怎么做的步骤（代码步骤必须有代码块）
- 引用了任何任务里都没定义的类型、函数或方法

记住：路径永远精确；每一步有完整代码；命令带期望输出。

## 自审

写完整份计划后，带着新鲜的眼光对照单正文 / 设计再看一遍。这是你自己跑的清单，不派子 Agent：

1. **覆盖**：单正文与设计的每一节 / 每条要求，能指出实现它的任务吗？列出缺口。
2. **占位扫描**：按上一节的句式搜一遍，修掉。
3. **类型一致**：后面任务用的类型、签名、属性名和前面任务定义的一致吗？任务 3 叫 `clearLayers()`、任务 7 叫 `clearFullLayers()` 就是 bug。

发现问题就地修，不用再审一轮；发现没有任务覆盖的要求就补任务。

## 交给执行

计划随单上传后：执行者用 workflow-execute 领单，读单时把附件一并拉全（read-card 四路），按计划逐步做；步骤勾选只是内部进度，完成以 workflow-execute 的四件硬性交付为准。多张单并行时由主 loop 用 workflow-dispatch 扇出，本计划只管单张单内部的步骤。
