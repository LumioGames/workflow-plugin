# 规划阶段、执行轨道与质量闸门

本文件定义蓝图的逻辑依赖，不授权规划 Agent 启动实现。只生成实际需要的阶段；标题顺序不是要求每个项目都创建同一组卡。

## 需求定义与可选预研

- 复杂蓝图第一张固定为 `[原始需求]`，保存输入、附件、决策账本、范围、非目标和变更影响；它是来源记录，不是待执行的专业任务。
- 按需生成 `[策划]` 或更具体的系统、玩法、关卡、叙事、经济/数值卡，锁定下游必须共享的规则、内容合同与成功指标。
- 能在规划对话中决定的产品问题先决定；可由专业执行者判断的细节要写清决策权限和边界，不把所有实现细节伪装成产品决定。
- 必须通过原型、测量或评审才能消除的高风险未知，先生成 `[预研]`：写明假设、时间盒、最小原型、证据、决策人、通过/停止阈值和对下游的影响。若结论会改变下游合同，先只保留条件化提纲；结论锁定后再生成并授权正式生产卡，不基于猜测提前落单或并行开工。

## 体验、内容与资产设计

- 按需生成 UX/UI、关卡/内容、叙事/本地化、美术、技术美术、动画、VFX、音频等卡；共享 Brief 和接口稳定后，交付范围不重叠的卡可以并行。
- 每张卡交付版本明确、可消费和可验收的规格或资产：包括状态/变体、源文件、命名与导出、导入设置、预算、授权来源和偏离规则中的适用部分。
- 需要进引擎验证的资产或内容，不能以源文件“看起来完成”代替目标平台、目标镜头或实际交互中的验证。

## 测试与验证设计

- 对代码和玩家可见行为，在生产实现前把已锁需求转换为风险驱动的用例与可自动化合同；每张实现卡列明自己消费的用例族。
- 按需覆盖正常链、边界、权限、失败恢复、兼容、存档/迁移、联网/重连、性能、视觉、输入设备、无障碍、本地化、遥测、平台认证、集成、E2E 和回归，不机械要求全部类别。
- 对纯资产、内容或运营配置，生成领域评审、导入检查、在机/在引擎验证和回滚检查；没有代码就不创建空的 TDD 或 Code Review 卡。

## 共享合同与公共底座(接口先行 —— 硬规则)

- **接口冻结是第一张可执行卡**（或原始需求内的强制接口节），先于一切消费方卡片；未冻结前，消费方只能保留条件化提纲。
- 必须冻结的适用面：API/DTO、网络协议、存档与数据 schema、内容格式、公共接口、构建管线、错误语义和共享测试夹具；每项以可引用物（单号/tag/commit/文件路径）指明。
- 普通消费边（`basis=interface`）只能指向接口冻结物；不把提供方的实现状态当成消费方前置。
- 收尾/联调、发布或迁移等确需等待实现的边使用 `basis=implementation`；逐条写明不可解耦理由并确认。
- 合同必须包含版本、兼容、迁移、回滚、遥测与性能预算中的适用部分。高风险协议、安全边界或不可逆迁移可安排早期定向评审，但不替代最终集成审查。
- 冻结后，客户端、服务端、工具、内容生产和公共能力**默认全部并行**：对着冻结接口与假件(stub/mock)开发；同一 wave 的可变文件/资产范围不得重叠。新蓝图按“总需求/Room → 公共接口/产出 → 可并行执行卡 → 收尾联调/验收卡”组织。
- 蓝图必须报告**最长依赖链深度**与**并行宽度**；链深 > 3 时向用户说明并确认。分析字段使用 `longestChainCards` 与 `parallelWidth`，并行宽度不是上传网络并发数。

若消费方确实需要上游最终产物，先拆出接口、fixture、导出包或其他最小公共产出；仍无法拆分时才标为阻塞，写明等待对象、不可解耦理由和解除条件，并记入决策账本。后续发现旧单依赖时只创建增量 bundle，读取并引用旧单，不修改旧 bundle；旧单未完成但接口已冻结时继续并行，接口和公共产出都不存在才阻塞。场景、Prefab、关卡、二进制资产、锁文件和生成清单等共享热点指定唯一所有者。

## 程序实现与内容生产

- 按独立交付物和责任边界拆卡。明确拥有的目录、系统或资产集合；无法提前精确到文件时写清边界和共享热点，执行者扩大范围前必须报告。
- 同一 wave 不允许两个 Agent 修改同一可变范围。场景、Prefab、关卡、二进制资产、锁文件、生成清单等难合并热点指定唯一所有者；其他卡通过稳定接口或交付包消费。
- 对可自动化的代码行为执行 Red → Green → Refactor：先让能证明目标行为的测试因缺少实现而失败，再写最小实现并通过相关与回归测试。不得制造无关失败或伪造测试输出。
- 若目标行为确实没有可自动化测试缝，卡片必须在开工前声明原因、补充最近层级的合同/仪器化/手工验证，并记录测试性缺口；不能用低价值假测试冒充 TDD。

## 集成候选与整体 Review

- 各卡先进入可回滚的集成候选并完成集成验证；在最终合入受保护分支、发布或状态完成前，对共同基线到集成候选的完整 diff/资产变更做一次整体 Review。
- reviewer 在可行时独立于实现者，对照原始需求、专业卡、测试合同、项目规则和真实验证证据，审查正确性、安全、合同、数据边界、性能、资产预算、错误处理和知识同步。
- 不为每张低风险卡机械创建 reviewer 循环；高风险合同或迁移允许早期定向评审。最终 Review 仍要覆盖组合后才出现的集成问题。

## 最终 QA 与领域验收

- 整体 Review 放行后，执行适用的自动化、集成、E2E、在机/在引擎、视觉、性能、兼容、认证与手工验收；纯文档或资产交付使用相应领域验收，不虚构代码 QA。
- 代码问题退回对应实现/集成卡，资产或内容问题退回实际所有者；修复后复跑受影响验证和必要回归，并让 Review/验收闸重新确认受影响范围。
- 全部适用闸门有读回证据后，才允许完成专业 Requirement；Room 是否归档由蓝图明确的完成条件和有权限的执行流程决定。

## 简单需求的内嵌质量路径

- 简单代码需求在同一提示词内包含测试设计、Red-Green-Refactor（或经说明的替代验证）、自审、交付级 Review 与最终 QA，不为这些活动单独建 Room。
- 简单资产、内容、文档或配置需求只内嵌适用的专业评审、导入/运行验证和回滚检查，不生成空的程序阶段。
- 简单预研需求只承诺证据和决策结论，不把原型冒充生产交付。
