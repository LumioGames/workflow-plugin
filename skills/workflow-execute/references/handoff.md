# 证据评论模板与交回格式

## 一、完成回写的证据评论（统一结构，让验收方机械核对）

`POST /comments`，`targetType` 按对象取 `requirement` / `work_item` / `bug`，`body` 用下面的 Markdown 模板。小节一个不少：没有内容的写「无」，**不留空标题、不自由发挥**——验收方要拿这份结构逐条对验收项。

```markdown
## 执行交付：<displayKey> <标题>

- 执行者：<Agent 名或脱敏标识>
- 时间：YYYY-MM-DD HH:mm（时区）
- 交付位置：<仓库 + 分支 + 提交号；非代码交付写产物路径与版本>

### 改动清单
- <实际变更，按文件 / 资产 / 配置逐条；含新增、修改、删除>

### 提交单号
- <仓库名>：<Git commit hash / 分支 / PR 链接，或 SVN revision 号>；多仓库逐行列
- 没有代码提交的交付（纯配置、纯资产上传等）写明原因；**有提交却不写单号，验收方无法追溯，视为未交付**

### 验收对照
按卡上验收项原文与顺序逐条对：
1. <验收项原文> —— 通过 / 未覆盖 —— 证据：<命令 + 关键输出摘要，或截图附件文件名>

### 实际运行的验证
- `<命令>` → <关键输出或结论>
（没跑的写「未执行」；不得用计划中的验证冒充结果——G7）

### 决策记录
- <开工前讨论确认的取舍：问题 → 谁拍板 → 结论>；没有写「无」

### Known gaps 与遗留补单
- <未覆盖项、已知风险>；没有写「无」
- **这次不做的 TODO / 降优先级项，每条必须对应一张已落库的补需求单**：<遗留事项> → <补单 displayKey>（模式二写「补单草稿见交回报告」）。只在评论里提一句而不落卡 = 沉默丢弃，禁止；用户明确决定不补单的，写明「用户决定不补：<原因>」

### 边界声明
- <本次没做什么；与卡内要求的偏离及原因>；没有写「无」
```

纪律：证据只写实际执行过的命令与真实输出（G7）；不贴 token、凭据、个人数据或整段无关日志（G4）；引用原单附件写文件名，不重复上传。

## 二、交接纪要（`POST /handoffs`，写给下一棒的人）

证据评论是给验收方逐条核对的，长；交接纪要是给**接力的人**的，短——下一棒读一眼所属需求室最近几条纪要就知道落点，不必逐张单翻证据评论。`summary` 固定三行纯文本，**合计 ≤200 字符**（字符语义，中文一个字算一个）：

```text
做了什么：<这次实际落地了什么，不复述背景>
怎么交接：<下一棒要知道的落点——分支/产物在哪、卡在什么条件上、谁在等谁>
交接文档在哪：<证据评论深链 / 文档 displayKey / 产物路径>
```

- **超 200 字符要重写，不要截断**——被截掉的恰好是最要紧的「交接文档在哪」。压不下来就砍第一行的细节，不砍第三行。
- `handoffRef` 是独立字段（上限 500 字符），优先填刚写的那条证据评论的深链；`summary` 第三行写人读得懂的落点名，两者不冲突。
- 纯文本：不写 Markdown 结构、不贴命令输出、**不写 token / 凭据 / 个人数据**（G4）。绑了飞书群的需求室会把纪要镜像进群，读者比单据本身多一圈。
- `agentLabel` 标明**是哪个仓库的 Agent** 写的（`client` / `server` / `game` 之类的小写 slug，上限 40 字符，同一仓库内保持稳定），**必填且不猜**：按 [connection.md](../../workflow-ops/references/connection.md) 第一节的优先级取，都拿不到就在 [execute-flow.md](execute-flow.md) 第四节梳理时问用户一次，并把答案记进决策记录。它只是来源标签，不参与鉴权、不构成身份。

## 三、模式二（无凭证）的交回报告

执行 Agent 不持凭证时，交回物必须让调度方**不追问一句**就能代写。开工前的需求梳理与决策清单（execute-flow 第四节）作为**中间报告**先交调度方一轮，拿到答复才执行；完成后的会话报告固定六段：

1. **目标单**：displayKey + 标题（派遣 prompt 给了 UUID 就带上）。
2. **建议流转**：完成后建议的目标状态**语义**（如「待验收」）——具体 `toStateKey` 由持凭证方现查 transitions 决定，报告里不猜状态 key（G6）。
3. **证据评论正文**：按第一节模板写完整 Markdown，调度方原样 `POST`，不需要改写。
4. **附件清单**：本地文件绝对路径 + 每个文件证明哪条验收项（调度方按清单上传后，评论正文里的文件名要能对上）。
5. **交接纪要草稿**：按第二节写好的三行 `summary` + `agentLabel`（拿不到就写「待调度方确定」并说明），由调度方 `POST /handoffs`。
6. **Known gaps、遗留补单草稿与边界声明**：与评论正文一致地再列一遍；每条遗留 TODO / 降优先级项附一份按 [card-spec.md](../../workflow-ops/references/card-spec.md) 写好的补单草稿（标题 + 背景/目标/验收/边界四节，正文注明来源单），由调度方落单后把 displayKey 填回评论——调度方要据此决定是否流转、是否先退回。

模式二还必须附上 **bundle 状态**：`bundleId`、`checkpoint`（`ready` / `pending upload` /
`partial` / `complete`）、`concurrency`、已验证/失败/阻塞操作数和可恢复路径。依赖分析另列
direct edge、传递链、当前阻塞链、Provider 与 `native` 状态；关系未上传或未读回时写“待上传”，
不能把分析结果说成已建立关系。

调度方代写时按 [execute-flow.md](execute-flow.md) 第七节的顺序执行并逐步读回；代写完成后把 displayKey + 链接 + 读回结果回给执行侧与用户留档（G3：没读回不说已回写）。

## 四、向用户交回（两种模式通用）

1. 单号 + 标题 + 链接 + 当前状态（模式一写读回确认的状态；模式二写「待调度方回写」）。
2. 已回写 / 待代写的评论与附件清单。
3. 验收对照结论摘要（几条通过、几条未覆盖）。
4. Known gaps 与边界声明。
5. 失败与遗留：没成功的调用列状态码 + `traceId`；部分成功说部分成功。
